## 1. Быстрый старт

**Требования:** Windows, .NET 8 SDK, Visual Studio 2022 (или Rider) с поддержкой WPF.

```bash
# сборка
dotnet build LABA_3/LABA_3.slnx

# запуск
dotnet run --project LABA_3/LABA_3/LABA_3.csproj
```

Либо открыть `LABA_3/LABA_3.slnx` и нажать F5.

Параметры проекта (`LABA_3/LABA_3.csproj`):

```xml
<TargetFramework>net8.0-windows</TargetFramework>
<UseWPF>true</UseWPF>
<Nullable>enable</Nullable>
<ImplicitUsings>enable</ImplicitUsings>
<AllowUnsafeBlocks>true</AllowUnsafeBlocks>
<OutputType>WinExe</OutputType>
```

Размер окна задан в `MainWindow.xaml`: 900×700.

**Как пользоваться заданием 3:**

1. Открыть вкладку «Задание 3».
2. Кликнуть по холсту в трёх местах — задаются вершины A, B, C.
3. Для каждой вершины выбрать свой цвет (по умолчанию красный / зелёный / синий).
4. Треугольник заливается автоматически. Внизу появляется строка с именем
   алгоритма, числом залитых пикселей и временем расчёта.

Кнопки: **Залить градиентом** (перерисовать), **Случайный** (случайный крупный
треугольник с тремя разными цветами), **Убрать точку**, **Очистить**,
**Сравнить алгоритмы** (самопроверка), чекбокс **Контур и вершины**.

```
              │                        │

              ▼                          ▼
┌─────────────────────────────────────────────────────────────┐
│ Drawing/                                                      │
│  GradientCanvas : LineCanvas : ──► PixelCanvas (abstract)    │
│  (заливка)        (отрезки)         буфер BGRA, WriteableBitmap, │
│                                    SetPixel / BlendPixel /     │
│                                    DrawLineBresenham            │
└─────────────────────────────────────────────────────────────┘
```

### Ключевое решение: общий базовый холст

Изначально у каждого задания был свой класс-холст с копией одного и того же
пиксельного буфера. Это было исправлено: общая инфраструктура вынесена в
`PixelCanvas` (abstract), а `LineCanvas` и `GradientCanvas` её наследуют и
добавляют только свои алгоритмы.

Что это дало:

- **нет дублирования.** Заливка белым, запись пикселя, вывод на экран,
  альфа-смешивание, алгоритм Брезенхема — написаны один раз;
- **задание 3 переиспользует алгоритм Брезенхема из задания 2** для контура
  треугольника (наследует `DrawLineBresenham`);
- **задание 1 сможет добавиться без третьей копии** инфраструктуры: достаточно
  `class FillCanvas : PixelCanvas`;
- **публичный API задания 2 не сломан.** `LineDrawingControl.xaml.cs` не
  изменён ни на строку: `LineCanvas.Width`, `.Height`, `.Bitmap`, `.Clear()`,
  `.DrawBresenham(...)`, `.DrawWu(...)` доступны и через базовый класс
  (константы наследуются, обращение `LineCanvas.Width` разрешается как раньше).

### Слои абстракции внутри `PixelCanvas`

| Уровень | Что делает |
|---|---|
| Буфер | `byte[] _pixels` — BGRA, 4 байта на пиксель |
| Текстура | `WriteableBitmap Bitmap` — то, что видит WPF |
| Вывод | `UpdateBitmap()` — одна операция на кадр |
| Рисование | `SetPixel`, `BlendPixel`, `DrawLineBresenham` |
| Сервис | `Clear`, `PackColor`, константы размеров |

### Поток «событие → картинка»

Ни один пиксель не рисуется по одному в WPF. Все изменения идут в массив,
и на экран картинка отдаётся **целиком одним вызовом** `UpdateBitmap()`.
Это главное правило производительности проекта.

## 4. Общий пиксельный холст `PixelCanvas`

Файл: `Drawing/PixelCanvas.cs`

### Хранилище

```csharp
public const int Width = 600;       // ширина холста
public const int Height = 450;      // высота холста
protected const int Stride = Width * 4;        // байт в строке пикселей
protected const int PixelCount = Width * Height;
protected const int NoPixel = -1;              // маркер «не залито»

private readonly WriteableBitmap _bmp;                              // картинка для UI
private readonly byte[] _pixels = new byte[Stride * Height];        // сами пиксели
```

Формат — `PixelFormats.Bgra32`: на пиксель 4 байта в порядке **B, G, R, A**
(синий, зелёный, красный, альфа). Индекс пикселя `(x, y)` в массиве:

```
index = (y * Width + x) * 4
```

Полный буфер: 600 × 450 × 4 = **1 080 000 байт**.

`NoPixel = -1` выбран потому, что упакованный цвет при альфа = 255 всегда
неотрицателен, а `-1` в битах — это `0xFFFFFFFF`. Таким образом, «не залито»
невозможно перепутать с любым реальным цветом.

### Методы

| Метод | Назначение |
|---|---|
| `Bitmap` | отдать `WriteableBitmap` в `Image.Source` |
| `Pixels` | прямой доступ к буферу для алгоритмов наследника |
| `Clear()` | залить белым (виртуальный — наследник сбрасывает свои счётчики) |
| `UpdateBitmap()` | скопировать буфер в текстуру (вызывать **один раз** в конце) |
| `SetPixel(x, y, Color)` | записать пиксель цветом, с проверкой границ |
| `SetPixel(x, y, int argb)` | то же упакованным AARRGGBB |
| `BlendPixel(x, y, color, alpha)` | смешать с тем, что уже нарисовано (сглаживание Ву) |
| `DrawLineBresenham(...)` | целочисленный отрезок, **без** вывода на экран |
| `PackColor(color)` | `Color` → `int` AARRGGBB |
| `FillWhite()` | приватная заливка буфера белым |

Конструктор сам создаёт `WriteableBitmap`, заливает буфер белым и делает первый
вывод — наследнику остаётся только дописать свои методы.

**Важная деталь про `DrawLineBresenham`:** он рисует в буфер, но **не** вызывает
`UpdateBitmap()`. Вызывающий решает сам: в задании 2 — сразу (один отрезок),
в задании 3 — один раз после отрисовки всего контура. Это позволяет не
перерисовывать текстуру на каждом отрезке.

### Упаковка цвета

```csharp
protected static int PackColor(Color color)
    => unchecked((int)((uint)color.A << 24 | (uint)color.R << 16 | (uint)color.G << 8 | color.B));
```

Приведения к `uint` обязательны: константа `0xFF000000` как знаковый `int`
равна −1, и без приведения получились бы битовые ошибки. Обратное преобразование
делает `SetPixel(int, int, int)`.

## 5. Задание 2: `LineCanvas`

Файл: `Drawing/LineCanvas.cs` — наследник `PixelCanvas`, добавляет только два
способа построения отрезка. Публичный API исходный, не тронут.

### Брезенхем (целочисленный)

```csharp
int dx = Math.Abs(x1 - x0), dy = Math.Abs(y1 - y0);
int sx = x0 < x1 ? 1 : -1, sy = y0 < y1 ? 1 : -1;
int err = dx - dy;
while (true)
{
    SetPixel(x0, y0, argb);
    if (x0 == x1 && y0 == y1) break;
    int e2 = 2 * err;
    if (e2 > -dy) { err -= dy; x0 += sx; }
    if (e2 < dx)  { err += dx; y0 += sy; }
}
```

Ни одной вещественной переменной → одинаковый результат на любом процессоре.
Алгоритм лежит в базовом классе и переиспользуется заданием 3.

### Ву (сглаживание)

Линия рисуется в два соседних пикселя по краям столбца, доля каждого
вычисляется из дробной части пересечения (`Fpart`) и смешивается с фоном через
`BlendPixel`. Перед отрисовкой отрезок приводится к «пологому» виду
(перестановка координат при `steep`), чтобы одна формула покрывала все случаи.

## 6. Задание 3: теория

### 6.1. Задача

Дан произвольный треугольник с **тремя разными цветами в вершинах**. Нужно
залить его внутреннюю часть так, чтобы цвет плавно переходил от вершины к
вершине.

### 6.2. Растеризация

Векторную фигуру нельзя показать на экране: экран — сетка пикселей.
**Растеризация** — процесс превращения примитива в набор пикселей:
«какие пиксели внутри фигуры и какого они цвета».

### 6.3. Треугольник = пересечение трёх полуплоскостей

Каждая сторона — прямая, а прямая делит плоскость на две половины. Треугольник —
это ровно та часть плоскости, что остаётся **с внутренней стороны всех трёх
сторон**. Отсюда универсальный способ проверки: «пиксель внутри тогда и только
тогда, когда он с внутренней стороны от всех трёх сторон».

### 6.4. Функция-полуплоскость (edge function)

Для стороны `a → b` и точки `p`:

```
E(p, a, b) = (b.x − a.x)·(p.y − a.y) − (b.y − a.y)·(p.x − a.x)
```

Это **удвоенная ориентированная площадь** треугольника `a, b, p`. Свойства:

- на самой стороне (`p` лежит на прямой `ab`) → `E = 0`;
- по одну сторону от прямой положительна, по другую — отрицательна;
- зависит только от направления `a→b`, положение `p` влияет линейно.

Знак зависит от того, в каком порядке перечислены вершины. Чтобы пользователю
не приходилось думать, в каком порядке он расставил точки, вводится нормализация:

```csharp
double area = SignedArea(v0, v1, v2);          // = E(A, B, C)
if (Math.Abs(area) < Epsilon) return;         // вырожденный треугольник
double orientation = area < 0 ? -1.0 : 1.0;    // знак обхода
double w = orientation * E(p, ...);            // внутри → w ≥ 0
```

После этого условие «пиксель внутри» одинаково для любого порядка вершин:
**все три `w` должны быть ≥ 0**.

### 6.5. Барицентрические координаты

Веса `(λA, λB, λC)`, для которых

```
P = λA·A + λB·B + λC·C,     причём  λA + λB + λC = 1
```

Смысл: точка P «собирается» из вершин в долях λ. Свойства:

| Точка | Веса |
|---|---|
| вершина A | (1, 0, 0) |
| центр масс | (1/3, 1/3, 1/3) |
| середина AB | (1/2, 1/2, 0) |

Барицентрические координаты получаются **из тех же edge-функций**:

```
λA = E(p, B, C) / S
λB = E(p, C, A) / S
λC = E(p, A, B) / S
где S = E(A, B, C) — удвоенная ориентированная площадь
```

(Сумма числителей тождественно равна `S`, поэтому λ в сумме дают ровно 1 —
это проверяемое свойство.)

### 6.6. Затенение Гуро

Цвет в точке — **та же линейная комбинация**, что и сама точка:

```
color(P) = λA·colorA + λB·colorB + λC·colorC
```

То есть ровно те же барицентрические веса, что и для геометрии, применяются к
цвету. Отсюда и градиент: у одной стороны преобладает цвет A, у другой — C,
внутри — смесь.

Каналы считаются независимо:

```
R = λA·R_A + λB·R_B + λC·R_C      (аналогично G и B)
```

**Ограничение подхода:** интенсивность задана только в вершинах, поэтому
перспективные искажения не учитываются (дальние грани должны быть тусклее —
здесь они такие же яркие). Это осознанное упрощение, заложенное в формулировку
задания. Метод Фонга решает эту задачу, пересчитывая цвет на каждый пиксель по
нормали поверхности, но это другая тема.

### 6.7. Правило пиксельного центра (почему `+0.5`)

Пиксель — не точка, а **квадрат**. У пикселя с индексом `(x, y)` центр лежит в
`(x + 0.5, y + 0.5)`.

- Если проверять принадлежность в левом верхнем углу пикселя, соседние фигуры
  будут заканчиваться на полпикселя раньше → получатся **щели**.
- Если в правом нижнем — фигуры будут **налезать** друг на друга.

Поэтому все проверки идут по центрам:

```csharp
int xStart = (int)Math.Ceiling(xMin - 0.5);   // первый пиксель, центр которого ≥ xMin
int xEnd   = (int)Math.Floor(xMax - 0.5);     // последний такой пиксель
double py  = y + 0.5;
```

### 6.8. Почему два алгоритма

Оба алгоритма заливают **одно и то же множество пикселей**, но обходят холст
по-разному:

- **сканлайн** идёт «строка → отрезок пересечения → пиксели отрезка»;
- **полуплоскости** идут «ограничивающий прямоугольник → проверка каждого пикселя».

Математически это одно и то же: на фиксированной высоте `py` каждая из трёх
полуплоскостей задаёт интервал по `x`, а их пересечение — это ровно тот самый
отрезок `[xMin, xMax]`.

Отсюда следует способ самопроверки: если после двух заливок пикселей
различается хоть один — значит, в одном из алгоритмов ошибка. В коде это метод
`CompareRasterizers` (кнопка «Сравнить алгоритмы»). Проверено на сотнях
треугольников: расхождений **0**.

## 8. Задание 3: `GradientCanvas` — построчно по логике

Файл: `Drawing/GradientCanvas.cs`, класс `sealed`, наследует `PixelCanvas`.

### Поля

```csharp
private const double Epsilon = 1e-9;                        // допуск
private readonly int[] _gradient = new int[PixelCount];     // промежуточный буфер
public int FilledPixelCount { get; private set; }           // счётчик залитых пикселей
```

**Зачем промежуточный `int[]`, а не писать сразу в пиксели:**

1. пиксели вне треугольника остаются нетронутыми белыми;
2. цвет считается в `double` и раскладывается по байтам в самом конце — так
   накапливается меньше ошибок округления;
3. результат можно сравнить с другим результатом попиксельно
   (используется в `CompareRasterizers`).

`NoPixel` (значение −1) помечает «здесь не залито».

### Публичные методы

#### `Clear()` (строка 25)

```csharp
public override void Clear()
{
    base.Clear();            // заливка белым + вывод
    FilledPixelCount = 0;    // сброс счётчика
}
```

Виртуальный метод базового класса позволяет наследнику сбросить вместе с фоном
своё состояние. Конструктор базового класса **не** вызывает `Clear()`, чтобы
виртуальный вызов не произошёл до инициализации полей наследника.

#### `DrawPolyline(...)` (строка 32)

Предпросмотр: когда задана только одна или две вершины, рисуется ломаная
(отрезки Брезенхемом) и маркеры в точках. Один вызов `UpdateBitmap()` в конце.

#### `RasterizeTriangle(v0, v1, v2, rasterizer, showOverlay)` (строка 49) — главный метод

```csharp
FilledPixelCount = 0;
Fill(v0, v1, v2, rasterizer, _gradient);         // 1. заливка в буфер

for (int i = 0; i < PixelCount; i++)              // 2. раскладка цветов в пиксели
{
    if (_gradient[i] == NoPixel) continue;
    FilledPixelCount++;
    int argb = _gradient[i];
    int index = i * 4;
    Pixels[index]     = (byte)(argb & 0xFF);                 // B
    Pixels[index + 1] = (byte)((argb >> 8) & 0xFF);          // G
    Pixels[index + 2] = (byte)((argb >> 16) & 0xFF);         // R
    Pixels[index + 3] = (byte)((argb >> 24) & 0xFF);         // A
}

if (showOverlay) DrawOverlay(v0, v1, v2);         // 3. контур и вершины поверх
UpdateBitmap();                                   // 4. вывод на экран
```

Шаг 2 идёт по всему холсту (270 000 итераций) — это дешевле, чем вставлять
проверку границ в растеризатор, и даёт точный подсчёт `FilledPixelCount`.

#### `CompareRasterizers(v0, v1, v2)` (строка 77)

Прогоняет оба алгоритма на двух временных буферах и считает позиции, где
результаты разошлись. Ноль — доказательство эквивалентности. Кнопка
«Сравнить алгоритмы» вызывает именно его.

### Алгоритм 1: `FillScanLine` (строка 107)

**Подготовка**

```csharp
Array.Fill(target, NoPixel);                       // сначала "не залито" везде

double area = SignedArea(v0, v1, v2);
if (Math.Abs(area) < Epsilon) return;              // вырожденный треугольник

double orientation = area < 0 ? -1.0 : 1.0;        // нормализация знака
double totalArea = Math.Abs(area);

int yTop    = ClampY((int)Math.Ceiling(MinY(v0, v1, v2) - 0.5));
int yBottom = ClampY((int)Math.Floor (MaxY(v0, v1, v2) - 0.5));
```

`yTop`/`yBottom` — строки, чей центр попадает в вертикальный диапазон
треугольника. Вычитание `0.5` — правило пиксельного центра. `ClampY` защищает
от выхода за границу холста, если вершина выставлена у самого края.

**Цикл по строкам**

```csharp
for (int y = yTop; y <= yBottom; y++)
{
    double py = y + 0.5;                            // центр строки

    // находим отрезок пересечения: самое левое и самое правое пересечения
    double xMin = double.PositiveInfinity;
    double xMax = double.NegativeInfinity;
    AccumulateCrossing(v0.Position, v1.Position, py, ref xMin, ref xMax);
    AccumulateCrossing(v1.Position, v2.Position, py, ref xMin, ref xMax);
    AccumulateCrossing(v2.Position, v0.Position, py, ref xMin, ref xMax);
    if (double.IsInfinity(xMin) || xMin > xMax) continue;   // строка не пересекает фигуру

    int xStart = Math.Max(0,        (int)Math.Ceiling(xMin - 0.5));
    int xEnd   = Math.Min(Width - 1, (int)Math.Floor (xMax - 0.5));
```

`AccumulateCrossing` (строка 213) решает уравнение прямой `ab` на высоте `py`:

```csharp
double dy = b.Y - a.Y;
if (Math.Abs(dy) < Epsilon) return;                     // горизонтальная сторона строку не режет
double px = a.X + (py - a.Y) * (b.X - a.X) / dy;         // параметрическое уравнение прямой
if (px < xMin) xMin = px;
if (px > xMax) xMax = px;
```

**Веса в крайнем левом пикселе строки**

```csharp
double px = xStart + 0.5;
double w0 = orientation * Edge(v1.Position, v2.Position, px, py);   // вклад вершины A
double w1 = orientation * Edge(v2.Position, v0.Position, px, py);   // вклад вершины B
double w2 = orientation * Edge(v0.Position, v1.Position, px, py);   // вклад вершины C
```

Индексы «перекручены» нарочно: `Edge(B, C, P)` — это вклад **противоположной**
вершины A, как и в формуле `λA = E(p, B, C)/S`.

**Приращения — главный приём оптимизации**

```csharp
double step0 = -orientation * (v2.Position.Y - v1.Position.Y);
double step1 = -orientation * (v0.Position.Y - v2.Position.Y);
double step2 = -orientation * (v1.Position.Y - v0.Position.Y);
```

Раскроем: `E(B,C,P) = (C.x−B.x)(P.y−B.y) − (C.y−B.y)(P.x−B.x)`. При увеличении
`P.x` на единицу это выражение меняется на `−(C.y−B.y)`. Значит, чтобы идти по
строке, **не пересчитывая** площади заново, достаточно прибавлять константу.
Три умножения вместо полного пересчёта на каждом пикселе.

**Внутренний цикл**

```csharp
for (int x = xStart; x <= xEnd; x++)
{
    if (w0 >= -Epsilon && w1 >= -Epsilon && w2 >= -Epsilon)
        target[y * Width + x] = PackBlend(v0.Color, v1.Color, v2.Color,
                                           w0 / totalArea, w1 / totalArea, w2 / totalArea);

    w0 += step0;  w1 += step1;  w2 += step2;         // сдвиг на пиксель вправо
}
```

Проверка `>= -Epsilon`, а не `> 0`, — чтобы пиксели, лежащие **точно на стороне**,
тоже заливались. Иначе на ровных (осевых) треугольниках по краю шла белая
ниточка. `w / totalArea` — это и есть барицентрические веса λ.

### Алгоритм 2: `FillEdgeFunctions` (строка 162)

```csharp
int xLeft   = Math.Max(0,        (int)Math.Floor (MinX(v0, v1, v2) - 0.5));
int xRight  = Math.Min(Width - 1, (int)Math.Ceiling(MaxX(v0, v1, v2) - 0.5));
int yTop    = Math.Max(0,        (int)Math.Floor (MinY(v0, v1, v2) - 0.5));
int yBottom = Math.Min(Height - 1,(int)Math.Ceiling(MaxY(v0, v1, v2) - 0.5));

for (int y = yTop; y <= yBottom; y++)
  for (int x = xLeft; x <= xRight; x++)
  {
      double w0 = orientation * Edge(v1.Position, v2.Position, px, py);
      if (w0 < -Epsilon) continue;          // ранний выход
      double w1 = orientation * Edge(v2.Position, v0.Position, px, py);
      if (w1 < -Epsilon) continue;
      double w2 = orientation * Edge(v0.Position, v1.Position, px, py);
      if (w2 < -Epsilon) continue;

      target[y * Width + x] = PackBlend(...);
  }
```

Отличия от алгоритма 1:

- границы — **ограничивающий прямоугольник** (bbox), никакой арифметики
  пересечений;
- все три веса считаются заново для каждого пикселя, зато с **ранним выходом**
  `continue` — «уже не внутри, дальше считать бессмысленно»;
- цвет считается той же формулой.

Компромисс: сканлайн быстрее на больших треугольниках (не обходит «углы»
прямоугольника, где заливки всё равно нет), вариант с полуплоскостями проще
в коде. Замеры в разделе 12.

### Вспомогательные функции

| Функция | Строка | Назначение |
|---|---|---|
| `Fill` | 93 | диспетчер: выбирает алгоритм по перечислению |
| `Edge` | 205 | функция-полуплоскость: `(b.x−a.x)(py−a.y) − (b.y−a.y)(px−a.x)` |
| `SignedArea` | 209 | удвоенная ориентированная площадь = `Edge(A, B, C)` |
| `AccumulateCrossing` | 213 | пересечение стороны с горизонталью |
| `PackBlend` | 227 | смешивание цветов по весам → AARRGGBB |
| `MixChannel` | 234 | округление доли канала до байта 0..255 |
| `MinX/MaxX/MinY/MaxY` | 242–256 | границы прямоугольника |
| `ClampY` | 258 | ограничение номера строки диапазоном холста |
| `DrawOverlay` | 261 | контур (3 отрезка Брезенхема) + 3 маркера |
| `DrawVertexMarker` | 275 | белый квадрат 7×7 с цветным центром 3×3 |
| `DrawMarker` | 292 | квадрат 7×7 с белым центром (предпросмотр) |

`PackBlend` смешивает каждый канал отдельно и упаковывает результат:

```csharp
unchecked((int)(0xFF000000u
    | ((uint)MixChannel(l0 * c0.R + l1 * c1.R + l2 * c2.R) << 16)
    | ((uint)MixChannel(l0 * c0.G + l1 * c1.G + l2 * c2.G) << 8)
    | MixChannel(l0 * c0.B + l1 * c1.B + l2 * c2.B)))
```

Приведения к `uint` обязательны (см. раздел 4). `MixChannel` отсекает результат
в 0..255 — при идеальных весах переполнения не бывает, но на границе может
проскочить 255.0000001 из-за накопления ошибок `double`.

## 9. Задание 3: интерфейс `GradientTriangleControl`

### Разметка (`Controls/GradientTriangleControl.xaml`)

Четыре «полосы» в `Grid` с высотами `Auto`:

| Строка | Содержимое |
|---|---|
| 0 | выбор алгоритма + 5 кнопок + чекбокс контура (`WrapPanel`, переносится) |
| 1 | цвет каждой вершины: плашка-образец + `ComboBox` для A, B, C |
| 2 | холст: `Border` 602×452 с `Canvas` 600×450, внутри `Image` и подписи A/B/C |
| 3 | `StatusText` (подсказка) и `InfoText` (технический вывод) |

Решения, которые стоит знать:

- **`WrapPanel` вместо `StackPanel`** — при нехватке ширины элементы переносятся,
  а не обрезаются.
- **`ScrollViewer` вокруг всего** — страховка: если пользователь уменьшит окно,
  появится полоса прокрутки вместо недоступных кнопок.
- **`Tag` у пунктов `ComboBox`** — `Content` это то, что видит человек,
  `Tag` — машинное имя значения перечисления. Надёжнее, чем сравнивать строки.
- **`Image IsHitTestVisible="False"`** — чтобы картинка не перехватывала клики;
  кликает `Canvas`.
- **Подписи вершин — это `TextBlock` поверх `Canvas`**, а не пиксели холста:
  так они получают шрифт, тень (`DropShadowEffect`, задаётся в коде) и не портят
  картинку. Позиционируются через `Canvas.SetLeft/SetTop`.
- **`InfoText` моноширинным шрифтом** (`Consolas`), чтобы числа не «прыгали».

### Логика (`Controls/GradientTriangleControl.xaml.cs`)

Поля:

```csharp
private readonly GradientCanvas _canvas = new();                 // холст
private readonly List<GradientVertex> _vertices = new();         // 0..3 вершины
private readonly Random _random = new();                         // для «Случайный»
```

#### Флаг `_ready` — важная деталь

Когда WPF создаёт элементы из XAML, он **сразу** применяет свойства из разметки,
в том числе `SelectedIndex="0"`. Это порождает событие `SelectionChanged` →
обработчик → `Render()` → обращение к элементам, которых **ещё нет** → падение
при запуске. `Render()` начинается с `if (!_ready) return;` — события во время
`InitializeComponent()` игнорируются.

#### Ввод мышью

```csharp
private void Canvas_MouseLeftButtonDown(object sender, MouseButtonEventArgs e)
    => AddVertex(e.GetPosition(DrawingCanvas));

private void AddVertex(Point position)
{
    int x = (int)Math.Round(position.X);
    int y = (int)Math.Round(position.Y);

    if (x < 0 || x >= GradientCanvas.Width || y < 0 || y >= GradientCanvas.Height) return;

    if (_vertices.Count == 3) _vertices.Clear();     // 4-я точка начинает новый треугольник

    _vertices.Add(new GradientVertex(new Point(x, y), VertexColor(_vertices.Count)));
    Render();
}
```

Обработчик намеренно состоит из одной строки: `e.GetPosition` переводит
координату **в систему холста**, а вся логика вынесена в `AddVertex`, который
можно вызвать из теста без мыши.

#### `Render()` — единая точка перерисовки

```csharp
if (!_ready) return;

if (_vertices.Count == 3)
{
    SyncVertexColors();
    var watch = Stopwatch.StartNew();
    _canvas.RasterizeTriangle(_vertices[0], _vertices[1], _vertices[2],

    InfoText.Text = $"алгоритм: {SelectedRasterizerName}; залито {_canvas.FilledPixelCount} из {total} " +
                    $"пикселей ({100.0 * _canvas.FilledPixelCount / total:0.00}%); " +
                    $"время {watch.Elapsed.TotalMilliseconds:0.###} мс";
}
else
{
    _canvas.Clear();
    if (_vertices.Count > 0)
        _canvas.DrawPolyline(_vertices.Select(v => v.Position).ToList(), Colors.Black);

UpdateLabels();
```

`Render()` вызывается **от** каждого события (клик, смена цвета, смена
алгоритма, чекбокс, кнопки) — это единственный путь, ведущий к картинке.

## 11. Граничные случаи

| Ситуация | Поведение | Где обработано |
|---|---|---|
| Три точки на одной прямой (вырожденный треугольник) | Заливка не выполняется, счётчик 0, падения нет | `FillScanLine` / `FillEdgeFunctions`, проверка `Math.Abs(area) < Epsilon` |
| Вершины заданы в обратном порядке | Результат тот же | Нормализация `orientation` по знаку площади |
| Клик за пределами холста | Игнорируется | `AddVertex`, проверка границ |
| Вершина у самого края холста | Заливка корректно обрезается краями холста | `Math.Max/Min` + `ClampY` |
| Треугольник больше холста | Заливается видимая часть | Обрезка по `Width`/`Height` |
| Пиксель лежит ровно на стороне | Заливается (нет белой ниточки) | `w >= -Epsilon` вместо `w > 0` |
| Вершина заменяется 4-й точкой | Начинается новый треугольник | `AddVertex`: `if (_vertices.Count == 3) _vertices.Clear();` |
| Пользователь уменьшил окно | Появляется полоса прокрутки | `ScrollViewer` |
| Событие пришло во время `InitializeComponent` | Игнорируется | Флаг `_ready` |
| Горизонтальная сторона треугольника | Не делит строку пополам, а игнорируется при поиске пересечений | `AccumulateCrossing`: `|dy| < Epsilon → return` |
| Цветовые компоненты вышли за 0..255 | Отсекаются | `MixChannel` |

## 12. Производительность

Замеры на тестовом треугольнике (25510 пикселей, 9,45 % холста), Release-сборка,
запуск в тестовом харнесе:

| Алгоритм | Время | Комментарий |
|---|---|---|
| Сканлайн + барицентрические | ≈2,4–4,9 мс | не обходит пустые углы прямоугольника |
| Полуплоскости (edge functions) | ≈5,7–8,4 мс | проще в коде, пересчитывает веса на каждом пикселе |

Треугольник во весь холст: 134 476 пикселей (49,81 %), ≈29 мс.

Что даёт скорость:

1. **Итеративные приращения** вместо пересчёта площадей (сканлайн);
2. **Один `UpdateBitmap()`** на кадр, а не на пиксель или на отрезок;
3. **Ранний выход** по первой невыполненной полуплоскости (edge functions);
4. **Целые числа** в Брезенхеме.

Что можно улучшить (в порядке приоритета):

- считать заливку сразу в `byte[]`, минуя `int[]` (экономия ~1 МБ и прохода);
- хранить градиент построчно (кэш-линейный доступ);
- в edge functions начинать с самой «длинной» стороны (отсечение дешевле).

## 13. Тестирование

Алгоритмы тестировались **без окна** — через временные консольные проекты
вне репозитория (в папке `Temp`), которые подключают исходники задания 3

### Что проверялось

**Математика (все проверки пройдены):**

- 200 случайных треугольников + осезадатые + с вершинами на пиксельных
  центрах + обрезанные краями холста + краевые;
- `CompareRasterizers` → **0 расхождений** во всех случаях;
- число залитых пикселей совпало с наивным перебором «point-in-triangle» по
  всем 270 000 пикселям;
- цвет в вершине = цвет вершины, в центре масс = среднее арифметическое трёх
  цветов;
- альфа всегда 255;
- вырожденные треугольники → 0 пикселей, падения нет.

**Интерфейс (харнес создаёт окно, отдаёт команды, рендерит в PNG):**

- вершины ставятся ровно в заданные точки, подписи — на `+7 / −20`;
- клик вне холста игнорируется;

## 15. Ограничения и идеи развития

**Ограничения (осознанные):**

- только Гуро-затенение, перспективные искажения не учитываются;
- один треугольник за раз;
- нет учёта перекрытий между фигурами (нет правила top-left ownership);
- заливка всегда непрозрачная (альфа = 255);
- холст фиксированного размера 600×450.

**Куда можно развивать:**

- правило top-left ownership для корректной заливки набором фигур без щелей
  и наложений;
- альфа-канал в `GradientVertex` → полупрозрачный градиент;
- заливка произвольного многоугольника тем же сканлайном (even–odd и
  non-zero);
- сглаживание границ (антиалиасинг по площади покрытия, MSAA-подобный подход);
- Фонг-затенение с интерполяцией нормалей;
- интерактивный drag вершин (сейчас точки только ставятся и убираются).

## 16. Вопросы, которые задают на защите

**1. Почему два алгоритма, если достаточно одного?**
Они обходят холст по-разному (строки против прямоугольника), но описывают одно
множество пикселей. Это и проверка корректности, и сравнение скорости:
кнопка «Сравнить алгоритмы» показывает 0 расхождений.

**2. Как исключены двойные заливки и щели?**
Пиксель — квадрат, поэтому все проверки идут по его центру `(x+0.5, y+0.5)`,
а решение «внутри/нет» принимается один раз на пиксель. Для одного треугольника
перекрытия не бывает по построению. Для набора фигур понадобилось бы правило
top-left ownership.

**3. Что если вершины заданы в обратном порядке?**
Нормализация `orientation` по знаку ориентированной площади делает условие
«внутри» одинаковым при любом порядке обхода.

**4. Что с вырожденным треугольником?**
`|площадь| < 1e-9` → заливка не выполняется (`Array.Fill` оставляет буфер пустым),
счётчик 0, приложение не падает.

**5. Вершины за краем холста?**
Считаются в любой системе координат. `AddVertex` отсекает клики вне холста, а
заливка зажата `Math.Max`/`Math.Min`, поэтому пиксели за границу не пишутся.
Проверено тестом.

**6. Это Гуро или Фонг?**
Гуро: цвет — линейная комбинация цветов вершин с барицентрическими весами.
Перспективные искажения не учитываются — осознанное упрощение.

**7. Зачем `int[]`-буфер, если есть `byte[]`?**
Чтобы смешивать цвет в `double` и иметь возможность сравнить два результата
попиксельно. В `byte[]` сразу терялась бы точность, и «не залито» нельзя было бы
отличить от «залито чёрным».

**8. Почему `NoPixel = -1`?**
Признак «не залито» должен быть невозможен как цвет. При альфа 255 упакованное
значение неотрицательно, а `-1` в битах — `0xFFFFFFFF`. Такой комбинации как
«цвет» быть не может.

**9. Зачем общий `PixelCanvas`?**
Чтобы не было трёх копий пиксельного буфера, когда добавится задание 1. Задание 3
переиспользует алгоритм Брезенхема из задания 2 через наследование.

**10. Чем задание 3 отличается от задания 2?**
Там вопрос — «какие пиксели занять и с какой альфой» (Брезенхем / Ву). Здесь —
«какие пиксели занять и каким **цветом**» (Гуро). Общее — построчный обход и
целочисленные веса; в Брезенхеме вес это `err`, здесь — барицентрические `λ`.

**11. Почему проверка `>= -Epsilon`, а не `> 0`?**
Чтобы пиксели, лежащие ровно на стороне, тоже заливались. Иначе на осезадатых
треугольниках по краю шла белая ниточка толщиной в пиксель.

**12. Почему `-0.5` в границах?**
Правило пиксельного центра: центр пикселя `x` равен `x + 0.5`, поэтому
`ceil(xMin - 0.5)` даёт первый пиксель, центр которого попадает в отрезок.
